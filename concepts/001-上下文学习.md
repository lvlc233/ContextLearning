# 上下文学习

## 问题从哪里来

Agent 领域从 2023 年开始快速发展。围绕 Agent 工程，已经出现了许多不同方向的探索，例如运行环境、运行引擎、工具调用、memory、skill、自迭代、工作流编排等。

这些方向可以粗略拆成三个问题：

| 研究方向 | 代表内容 | 回答问题 |
| --- | --- | --- |
| Agent 运行环境 | sandbox、harness 等 | Agent 在哪运行？ |
| 运行引擎 | ReAct 范式、loop、dynamic workflows 等 | Agent 如何运行？ |
| 上下文管理 | CLAUDE.md、skill、memory 等 | Agent 要运行什么？ |

本文讨论的是第三类问题中的一部分：上下文内容的分析与迭代。

在 LLM 时代，Agent 行为并不只由模型参数决定。同一个模型，在加载不同 system prompt、skill、memory、工具说明或项目规则后，可能会表现出不同的回答方式、任务边界、工具选择和交互习惯。反过来，不同模型即使加载相同的上下文信息，也可能因为模型能力、运行环境、工具权限和执行机制不同，表现出不同的 Agent 行为。

这意味着：即使 Agent 行为会受到模型能力、运行环境、执行机制等因素影响，上下文信息仍然值得被单独分析、研究和讨论。

## 为什么需要上下文学习

如果上下文优化缺少明确的评估依据，修改就很容易变成一种经验性操作：看到一次输出不满意就即时补改，或者还没有运行反馈就凭感觉预设规则。

这种操作常见地表现为：

```text
这次输出不好，就补一条规则。
某个案例失败了，就把案例写进去。
某个 Agent 表现不错，就`沉淀`它的表现为 skill。
规则冲突了，就再补一条优先级说明。
```

这些做法并不一定错误。它们在早期探索或单次任务中经常有效。但一旦某一段上下文信息进入长期使用阶段，它就不再只是服务于某一次任务，而是可能同时承载多个目标、多个任务场景、多个模型适配或多轮版本迭代，也会被反复修改、迁移、合并和复用。

此时，难点就不再只是判断某次修改是否有效，而是要解释上下文内容在长期使用中的作用、适用条件和潜在副作用。

因此，真正要追问的是：

```text
哪些修改真的改善了行为？
哪些规则只是覆盖了某个局部案例？
哪些信息开始互相冲突？
哪些内容已经变成噪声？
为什么同一份上下文换一个模型或运行环境后就失效？
...
```

真正需要被讨论的，不是如何继续积累零散的上下文优化经验，而是如何解释上下文信息与 Agent 行为之间的关系，并让上下文内容如何被分析、测试和迭代，成为一个可以被持续讨论的问题。

这正是 `上下文学习` 所在的位置。

## 上下文学习研究什么

`上下文学习` 研究的是在 Agent 领域中，系统如何不依赖模型参数训练，而是通过组织、修改、积累与使用 `上下文信息`，影响模型在指定运行环境中的行为表现的基础研究方向。

它不讨论现有的 Agent 架构、运行环境或上下文操作方式，也不是提出一种新的 Agent 进化框架或理论，而是旨在为上下文内容分析与迭代问题提供一个统一的讨论起点。
